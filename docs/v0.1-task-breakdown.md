# v0.1 开发任务、完成定义与测试计划

## 1. 目标和边界

`v0.1` 是一个可独立完成的单人教学垂直切片，不以“原版内容基本齐全”为目标。

范围固定为：

- 单人，英雄仅 Tovak。
- 精简 First Reconnaissance 场景。
- 约 16 张基础行动牌，以及完成教学局所需的最小高级行动、法术、单位和敌人集合。
- 日夜、Source 法力、手牌组合、横置牌、移动、探索、一个互动地点、完整四阶段战斗、伤牌、奖励、一次升级和轮末。
- 占位素材、中文界面、英文稳定逻辑 ID。
- 本地自动存档、手动存档、信息屏障撤销、事件日志和固定种子回放。
- 极简 HTML 排版；地图居中，信息和操作使用普通 DOM，不做复杂装饰。

不包括：其他英雄、完整原版内容、城市、合作攻城、PvP、Volkare、任务、战役、天气、Item Shop、Forgemasters 和在线多人。

## 2. 全局完成定义

单个任务只有同时满足以下条件才可标记完成：

1. 代码已经合入主开发分支，没有临时注释掉的规则或静默 fallback。
2. TypeScript strict 类型检查、lint 和该任务相关测试全部通过。
3. 新增规则行为至少有一个成功测试和一个拒绝/边界测试。
4. 命令失败时状态完全不变，并返回结构化错误码。
5. 规则代码不读取 DOM、浏览器时间、网络或未注入的随机数。
6. 新增状态可以序列化、反序列化，并通过 schema 校验。
7. 用户可见行为已在事件日志中留下可理解的记录。
8. 文档中的验收项有对应测试 ID，不能只凭人工观察通过。

建议统一命令：

```text
pnpm typecheck
pnpm lint
pnpm test
pnpm test:property
pnpm test:e2e
pnpm test:replay
```

在项目尚未建立这些命令前，任务 `V01-01` 负责创建它们。

## 3. 测试层级和命名

| 前缀 | 层级 | 用途 |
| --- | --- | --- |
| `UT` | 纯函数单测 | 坐标、支付、伤害、效果计算 |
| `CT` | 命令契约测试 | 给定状态执行命令，断言事件、新状态或错误 |
| `IT` | 引擎集成测试 | 多条命令跨模块完成一段规则流程 |
| `PT` | 属性/不变量测试 | 随机合法命令序列不能破坏状态 |
| `ST` | Schema/内容测试 | JSON、ID、引用、素材 alias 和存档版本 |
| `UI` | 组件测试 | 合法操作、禁用原因、选择请求和日志 |
| `E2E` | 浏览器测试 | 从新游戏到场景结束、刷新和撤销 |
| `GR` | Golden Replay | 固定 seed 和命令序列产生固定状态哈希 |

测试夹具不得依赖生产随机牌序。需要随机结果时必须显式传入 seed 或固定牌堆。

## 4. 里程碑

| 里程碑 | 包含任务 | 可交付状态 |
| --- | --- | --- |
| M0 基线冻结 | `V01-01` - `V01-03` | 范围、协议和内容清单稳定 |
| M1 无界面引擎 | `V01-04` - `V01-08` | 脚本可完成打牌、移动和探索 |
| M2 完整规则闭环 | `V01-09` - `V01-12` | 脚本可完成战斗、升级和轮末 |
| M3 浏览器可玩 | `V01-13` - `V01-15` | 浏览器可走完整教学局 |
| M4 发布门禁 | `V01-16` - `V01-17` | 存档、回放、兼容性和回归通过 |

`V01-01` 至 `V01-03` 应按顺序完成。进入 M1 后，地图任务和卡牌任务可以有限并行；进入 M3 前必须完成全部 M2 任务。

## 5. 任务明细

### V01-01 工程骨架和质量门禁

**目标**：建立 monorepo、Web 应用、纯规则包、内容包和统一测试命令。

**交付物**：

- `apps/web`、`packages/engine`、`packages/content`、`packages/content-schema`、`packages/test-kit`。
- TypeScript strict、React、Vite、Vitest、React Testing Library、Playwright。
- lint、格式化、类型检查和测试脚本。
- CI 在干净环境执行安装、类型检查、单测和构建。

**完成判定**：

- 空白 Web 页面可构建和启动。
- `engine` 不依赖 React、DOM 或 `apps/web`。
- 故意引入类型错误或失败测试时，CI 会失败。

**测试**：

- `ST-001`：所有 workspace 包可解析且不存在循环运行时依赖。
- `IT-001`：Web 应用成功导入 `engine` 的公开接口并完成生产构建。
- `E2E-001`：页面启动后显示版本号 `v0.1-dev`，无控制台错误。

**建议工作量/模型**：1-2 天，Terra High；配置疑难切 Sol High。

### V01-02 冻结 v0.1 内容和规则裁定

**目标**：把“约 16 张”和“少量敌人”等模糊描述变成确切清单。

**交付物**：

- `v0.1-content-manifest.json`：卡牌、敌人、地图板块、地点、单位、法术和升级奖励的准确 ID。
- 每个实体的英文逻辑 ID、中文显示名、来源和 v0.1 所需数值。
- `rules-decisions.md`：记录规则歧义、采用裁定、规则来源和影响测试。
- 明确场景胜利、失败、轮数和教学步骤。

**完成判定**：

- manifest 中没有 `TBD`、临时 ID 或无法解释的数字。
- 每个场景步骤引用的实体都在 manifest 中。
- 范围外实体无法被 v0.1 新游戏加载。

**测试**：

- `ST-010`：所有 ID 唯一且符合 `core.<type>.<name>` 命名规则。
- `ST-011`：所有交叉引用、翻译键和 asset alias 均存在。
- `ST-012`：启用 v0.1 manifest 后实体数量与冻结清单完全一致。
- `ST-013`：注入范围外实体时内容 lint 失败并报告准确路径。

**建议工作量/模型**：1-2 天，Sol High；规则冲突使用 Sol Xhigh 复核。

### V01-03 GameState、命令、事件和错误协议

**目标**：在写具体规则前固定引擎边界。

**交付物**：

- 最小可序列化 `GameState`、`GameConfig`、`GameView`。
- `createGame`、`getLegalIntents`、`executeIntent`、`projectView` 四个接口。
- 命令、领域事件、错误码和 schema 版本策略。
- 状态 hash 的规范化算法，排除纯 UI 字段。

**完成判定**：

- 创建同 seed 游戏时状态 hash 一致。
- 非法命令返回错误且输入状态、新状态和事件日志均不改变。
- 所有命令联合类型都有穷尽处理。

**测试**：

- `UT-020`：规范化对象键顺序不影响状态 hash。
- `CT-020`：未知命令被拒绝且状态引用内容不变。
- `CT-021`：非当前阶段命令返回 `WRONG_PHASE`。
- `PT-020`：随机生成可序列化基础状态，round-trip 后 hash 不变。

**建议工作量/模型**：2-3 天，Sol Xhigh。

### V01-04 确定性随机数、区域和基础 reducer

**目标**：建立可重放的洗牌和统一实体移动机制。

**交付物**：

- 带 seed 的 RNG，随机结果写入事件。
- 牌库、手牌、打出区、弃牌堆、移出游戏区、单位区和市场区。
- `EntityMoved`、`DeckShuffled`、`CardDrawn` 等事件和 reducer。
- 核心不变量检查器。

**完成判定**：

- 同 seed 洗牌顺序一致，不同 seed 至少在样本中产生不同顺序。
- 任意实体同一时刻只存在于一个容器。
- reducer 对同一事件输入是纯函数。

**测试**：

- `UT-030`：固定 seed 的洗牌快照稳定。
- `UT-031`：抽空牌库不会隐式洗弃牌堆。
- `CT-030`：移动不存在或位于错误区域的卡牌被原子拒绝。
- `PT-030`：随机执行一千次合法区域移动，不变量始终成立。

**建议工作量/模型**：2 天，Sol High。

### V01-05 卡牌使用、法力支付和最小效果 DSL

**目标**：完成基础行动牌的普通、强化和横置使用。

**交付物**：

- `gain`、`spend-mana`、`sequence`、`choose-one`、`conditional` 最小 DSL。
- Move、Influence、Attack、Block 和 Heal 临时资源池。
- Source 法力、纯法力、水晶和金/黑法力的昼夜限制。
- 打出卡牌的暂定组合、确认和取消命令。

**完成判定**：

- manifest 中 16 张基础行动牌均可由 DSL 表达，无卡牌专用 UI 逻辑。
- 同一张牌每回合只能选择普通、强化或横置中的一种。
- 支付失败不消耗法力、不移动卡牌。

**测试**：

- `CT-040`：白天金色法力可强化基础色行动牌。
- `CT-041`：夜晚金色法力被拒绝，错误为 `MANA_COLOR_UNAVAILABLE`。
- `CT-042`：横置非伤牌产生所选基础资源 1，伤牌不能横置。
- `CT-043`：同一张牌重复使用被拒绝。
- `IT-040`：多张牌组合后资源明细等于每个效果来源之和。

**建议工作量/模型**：3-4 天，Sol High；DSL 设计复核使用 Sol Xhigh。

### V01-06 玩家回合、日夜和轮结构

**目标**：建立普通回合、休息、轮末及昼夜切换的状态机。

**交付物**：

- 回合阶段和合法命令查询。
- 普通回合、标准休息、慢速恢复、宣布轮末。
- 回合结束清理、抽牌和第二轮开始的昼夜切换。
- Source 骰占用、归还和重掷。

**完成判定**：

- UI 无关脚本可完成一个普通回合、一个休息和一次新轮准备。
- 任一阶段只暴露合法命令；越阶段调用被拒绝。
- 回合结束顺序与规则规格一致。

**测试**：

- `CT-050`：普通回合最多执行一个行动。
- `CT-051`：标准休息必须弃一张非伤牌，慢速恢复只在全伤手牌可用。
- `CT-052`：牌库非空时不能宣布轮末。
- `IT-050`：从白天第一轮结束进入夜晚第二轮，Source 和手牌正确刷新。
- `PT-050`：随机合法回合命令不会跳过强制阶段。

**建议工作量/模型**：3 天，Sol High。

### V01-07 六边形地图、地形和移动

**目标**：实现与渲染无关的地图坐标、邻接、费用和英雄移动。

**交付物**：

- 轴向坐标、邻居、距离、板块到全局坐标转换。
- v0.1 地形费用和不可进入地形。
- 移动点支付、逐格移动、合法目标和可达范围查询。
- 安全空间判断接口。

**完成判定**：

- 地图逻辑完全位于 engine，不使用像素坐标。
- 可达范围和实际移动使用同一个费用计算器。
- Move 不足、非相邻和不可进入地形均有不同错误码。

**测试**：

- `UT-060`：六方向邻居、距离对称性和坐标转换正确。
- `UT-061`：v0.1 每种地形的昼夜费用表正确。
- `CT-060`：Move 不足时移动原子失败。
- `CT-061`：山脉/湖泊在无特殊效果时不可进入。
- `PT-060`：任意坐标 `a,b` 满足 `distance(a,b) = distance(b,a)`。

**建议工作量/模型**：2-3 天，Terra High；状态接口复核用 Sol High。

### V01-08 地图探索和场景初始化

**目标**：用固定场景配置创建地图，并允许合法揭示新板块。

**交付物**：

- 精简 First Reconnaissance setup。
- 板块堆、合法放置形状、空间/地点/未知敌人生成。
- 探索费用、板块揭示事件和信息屏障。
- 场景目标、失败条件和结束触发器。

**完成判定**：

- 固定 seed 创建出的起始状态和板块堆稳定。
- 只有地图合法边界可探索。
- 揭示后无法撤销到屏障之前。

**测试**：

- `CT-070`：非边界、Move 不足和错误阶段的探索分别被拒绝。
- `CT-071`：成功探索产生板块、空间、敌人和 checkpoint 事件。
- `CT-072`：探索后正式模式撤销到探索前返回 `INFORMATION_BARRIER`。
- `GR-070`：固定 seed 的前两次探索结果和状态 hash 固定。

**建议工作量/模型**：2-3 天，Sol High。

### V01-09 战斗遭遇和四阶段状态机

**目标**：完成远程/攻城、格挡、伤害、普通攻击四阶段骨架。

**交付物**：

- `EncounterState`、阶段转换和目标分配命令。
- 工事、普通/远程/攻城攻击类型。
- 物理、火、冰属性及抗性贡献计算。
- Swift、Brutal 和至少一个多段攻击能力。
- 可展开的数值来源明细。

**完成判定**：

- 每个阶段只接受该阶段合法效果。
- 多个敌人可分别攻击/格挡，不会把独立格挡错误合并。
- 每项最终数值可追溯到基础值和修正项。

**测试**：

- `CT-080`：工事敌人在远程阶段拒绝普通远程攻击，接受攻城攻击。
- `CT-081`：抗性使对应攻击贡献减半，并按已冻结裁定取整。
- `CT-082`：Swift 所需格挡翻倍，元素无效格挡贡献减半。
- `CT-083`：多段攻击必须逐段格挡。
- `IT-080`：一个远程击败、一个未格挡、一个普通攻击击败的混合遭遇正确结束。

**建议工作量/模型**：4-5 天，Sol Xhigh。

### V01-10 伤害、伤牌、单位和治疗

**目标**：实现未格挡攻击的完整后果及最小单位使用。

**交付物**：

- 英雄护甲、单位护甲、单位 Ready/Spent/Wounded。
- 伤害分配、伤牌进入手牌、单位承伤。
- Poison 或 v0.1 清单中选定的附加能力。
- 非战斗治疗和击倒状态。

**完成判定**：

- 受伤单位不能激活或再次承受普通伤害。
- 英雄受伤循环直到剩余伤害归零。
- 战斗期间治疗命令不可用。

**测试**：

- `CT-090`：普通单位承伤后进入 Wounded，攻击减去单位护甲。
- `CT-091`：受伤单位再次分配伤害被拒绝。
- `CT-092`：英雄获得正确数量的手牌伤牌。
- `CT-093`：战斗中治疗被拒绝；战斗外 1 Heal 移除一张英雄伤牌。
- `IT-090`：达到未修正手牌上限数量的战斗伤牌后进入 KnockoutState。

**建议工作量/模型**：3-4 天，Sol High。

### V01-11 地点互动、奖励和升级

**目标**：完成一个互动地点和场景所需的一次成长闭环。

**交付物**：

- 一个冻结的互动地点及其招募、治疗或购买能力。
- Influence 支付和声望修正最小实现。
- 战斗奖励队列、名望增加和升级线。
- 一次指挥升级或技能/高级行动选择请求。

**完成判定**：

- 同一互动中允许连续合法购买，余额不足时原子拒绝单次购买。
- 奖励与升级严格在回合末按顺序处理。
- 需要选择时生成可保存的 `DecisionRequest`。

**测试**：

- `CT-100`：不在合法地点或 Influence 不足时互动失败。
- `CT-101`：招募单位占用指挥槽，槽位已满时要求先处理选择。
- `CT-102`：跨越升级线时不会立即打断战斗。
- `IT-100`：战斗胜利、领取奖励、升级选择、抽牌按顺序完成。
- `ST-100`：未完成升级选择可保存和恢复。

**建议工作量/模型**：3-4 天，Sol High。

### V01-12 回合闭环和无界面教学脚本

**目标**：把前述模块接成一局可结束的精简教学场景。

**交付物**：

- 场景胜利、失败、轮数限制和终局摘要。
- 一条人类可读的固定命令脚本，从开局执行到胜利。
- 一条失败脚本和至少一条战斗失败后继续的脚本。
- 事件日志中的关键规则说明。

**完成判定**：

- 不启动浏览器即可运行完整教学局。
- 胜利、失败均由场景触发器决定，不由测试直接修改状态。
- 完成后的状态通过全部不变量检查。

**测试**：

- `IT-110`：固定脚本从 `createGame` 到 `scenario.won`。
- `IT-111`：耗尽轮数进入 `scenario.lost`。
- `IT-112`：失败战斗执行撤退/伤牌后仍可继续下一回合。
- `GR-110`：胜利脚本最终 hash、名望、轮数、牌区和日志摘要固定。

**建议工作量/模型**：2-3 天，Sol Xhigh。

### V01-13 极简 Web 游戏壳和地图显示

**目标**：让浏览器只显示必要信息，并把 engine 作为唯一规则权威。

**交付物**：

- 新游戏、继续游戏和游戏主页面。
- 居中的 SVG 六边形地图，普通 HTML 状态区、手牌区、行动区和日志区。
- 点击地图格查看详情；合法格突出，非法格仍可查看原因。
- 占位素材 alias 和缺图 fallback。

**完成判定**：

- React 只调用公开引擎接口，不复制地形费用或合法行动规则。
- 页面使用极简排版，不依赖复杂卡片、动画或美术即可操作。
- 1280x720、1440x900 和 1024x768 横屏无文本遮挡、横向页面溢出或关键按钮不可见。

**测试**：

- `UI-120`：只渲染 `getLegalIntents` 返回的可执行命令。
- `UI-121`：点击非法目标显示引擎返回的具体原因。
- `UI-122`：缺失图片时显示实体名称占位，不产生 broken image。
- `E2E-120`：新游戏后地图、Tovak、手牌、昼夜和 Source 均可见。
- `E2E-121`：三个目标视口截图无重叠，控制台无错误。

**建议工作量/模型**：3-4 天，Terra High；交互边界复核用 Sol High。

### V01-14 手牌、法力、选择请求和战斗 UI

**目标**：通过 UI 完成打牌组合、移动、互动和完整战斗。

**交付物**：

- 手牌普通/强化/横置模式选择。
- Source 法力选择和资源计算明细。
- 通用 `DecisionRequest` UI。
- 战斗阶段、敌人目标、格挡/伤害分配和攻击确认界面。

**完成判定**：

- 所有操作均提交 intent，页面不直接修改游戏状态。
- 当前阶段、尚缺数值、选择范围和确认结果清晰可见。
- 刷新发生在选择请求中间时可恢复相同界面。

**测试**：

- `UI-130`：同一卡牌切换使用方式时预览资源正确且未提前提交状态。
- `UI-131`：确认后命令只提交一次；重复点击不会重复结算。
- `UI-132`：DecisionRequest 未完成时其他普通命令不可操作。
- `E2E-130`：从手牌组合 Move 到地图移动成功。
- `E2E-131`：浏览器中完成四阶段战斗并显示每个数值来源。

**建议工作量/模型**：4-5 天，Sol High。

### V01-15 事件日志、错误说明和教学流程

**目标**：让玩家能够理解结算，不增加另一套规则判断。

**交付物**：

- 中文事件日志、错误码到中文说明的映射。
- 日志项可查看相关卡牌、敌人或地图格。
- First Reconnaissance 教学步骤由合法行动和场景状态驱动。
- 场景结束摘要。

**完成判定**：

- 每次资源变化、移动、探索、战斗结果、伤牌、奖励和升级都有日志。
- 教学提示不替代或绕过规则校验。
- 错误信息包含原因和当前可采取的下一步，不显示内部堆栈。

**测试**：

- `UI-140`：事件类型都有中文渲染器，未知事件使用明确 fallback。
- `UI-141`：点击战斗日志可打开参与实体详情。
- `E2E-140`：按教学提示可从开局走到场景胜利。
- `E2E-141`：故意执行非法动作时 UI 显示对应错误且游戏仍可继续。

**建议工作量/模型**：2-3 天，Terra High。

### V01-16 存档、恢复、撤销和日志导出

**目标**：保证浏览器刷新和可撤销操作不会破坏规则确定性。

**交付物**：

- IndexedDB 自动存档、至少一个手动槽和存档 schema。
- 最近 checkpoint 撤销；探索、抽未知牌等信息屏障限制。
- seed、内容版本、命令序列和事件日志 JSON 导出。
- 损坏/版本不兼容存档的明确错误页面。

**完成判定**：

- 任意允许阶段刷新后，恢复状态 hash 与刷新前相同。
- 恢复后继续执行与不中断执行产生相同终局 hash。
- 撤销不能改变已经揭示的随机结果。

**测试**：

- `ST-150`：完整状态和未完成 DecisionRequest 均可 round-trip。
- `IT-150`：可撤销的打牌组合恢复到 checkpoint，手牌和法力完全复原。
- `IT-151`：探索后的撤销不能越过信息屏障。
- `E2E-150`：战斗中刷新页面后恢复同一阶段和选择。
- `GR-150`：中途保存恢复与连续运行最终 hash 相同。

**建议工作量/模型**：3-4 天，Sol Xhigh。

## 7. 推荐执行方式

每次只给 Codex 一个任务编号，并同时提供该任务依赖的接口和测试 ID。例如：

```text
实现 V01-07。严格限制在六边形地图、地形费用和移动规则；先阅读
docs/development-rules-spec.md 与 docs/v0.1-task-breakdown.md。
完成 UT-060、UT-061、CT-060、CT-061、PT-060，并运行已有回归测试。
不要修改战斗、探索 UI 或范围外内容。
```

关键检查点建议使用：

- 完成 `V01-03` 后做一次架构审查，确认状态和事件协议没有 UI 耦合。
- 完成 `V01-08` 后运行第一条无界面移动/探索回放。
- 完成 `V01-12` 后冻结第一条完整 Golden Replay。
- 完成 `V01-14` 后做第一次完整浏览器教学局。
- 完成 `V01-16` 后专门审查确定性、存档和撤销，不同时增加新规则。

## 8. 工期估算和关键路径

按一名熟悉 TypeScript/React 的开发者配合 Codex 计算，建议预留 7-10 周，而不是把各任务最低天数直接相加。规则核对、测试修正和浏览器交互返工需要缓冲。

关键路径为：

```text
V01-01 -> V01-02 -> V01-03 -> V01-04 -> V01-05 -> V01-06
       -> V01-08 -> V01-09 -> V01-10 -> V01-11 -> V01-12
       -> V01-13 -> V01-14 -> V01-15 -> V01-16 -> V01-17
```

`V01-07` 可在 `V01-04` 后与 `V01-05` 并行，但必须在 `V01-08` 前完成。内容录入可在 schema 稳定后并行进行，但每批数据仍需经过内容 lint。
